# F11 — Live incident updates with Server-Sent Events

## Design and delivery guarantees

Server-Sent Events (SSE) are used because incident changes flow from the backend to read-only status-board clients; the browser does not need a persistent bidirectional channel. The browser's native `EventSource` automatically reconnects and sends the last received event ID.

Every successful incident create or update writes a full incident snapshot to the append-only `incident_events` table in the same database transaction as the incident and audit-log change. Writers lock one database row before inserting an event, ensuring generated event IDs follow commit order even when incident writes overlap. The event table's generated ID is the SSE event ID. The stream queries rows with IDs greater than the subscriber's cursor, in ascending order, in batches of at most 100. Events are retained in PostgreSQL so reconnecting after a network interruption or backend restart can replay missed changes.

The initial `GET /api/incidents` response includes `X-Incident-Event-Cursor`. Its incident snapshot and cursor are read in one repeatable-read transaction, avoiding a gap between loading the current data and opening the stream. The frontend connects to `GET /api/incidents/events?after=<cursor>`; the server resumes from the higher of the initial cursor and `Last-Event-ID`. The frontend ignores repeated or older IDs and upserts each incident by ID, preventing duplicate cards. Heartbeat comments keep idle streams active.

## Automated evidence

**Hand-predicted expected results before running:** a created incident writes a `CREATED` event containing its full snapshot; a snapshot exposes the latest event cursor; a new stream uses its requested cursor; reconnecting with a later `Last-Event-ID` resumes after that ID; after a batch is sent, the next poll starts after its last ID; repeated frontend event IDs do not create duplicate incidents.

Run the backend and frontend checks from the repository root:

```powershell
mvn -f backend/pom.xml verify
cd frontend
npm run typecheck
npm run test
npm run lint
npm run build
```

The backend tests use synthetic incidents and mock repositories; frontend tests use a mocked `EventSource`. They do not require a live account or external service.

Observed: `mvn -f backend/pom.xml verify` passed all 28 backend tests. Frontend `npm run typecheck`, `npm run test` (10 tests), `npm run lint`, and `npm run build` all passed.

## Manual kill-and-recover proof

The automated tests verify cursor resume and client deduplication. The required browser kill-and-recover recording is still pending:

1. Start the app with PostgreSQL and open the incident board. Wait for `Live updates: connected`.
2. In browser developer tools, take the frontend offline while leaving the backend and database online.
3. From a separate operator-authorized session, update a synthetic incident. Keep the frontend page open so its last event ID is retained.
4. Restart the backend without clearing PostgreSQL while the frontend remains offline.
5. Restore the browser connection. Verify the stream reconnects, replays the missed event, and updates the incident once. Record the event ID and a screenshot or short recording.

Do not use real campus incidents or expose credentials in the recording.

## Limits

SSE is one-way; future browser-to-server actions continue to use the authenticated REST API. The per-connection poll reads at most 100 rows each second, so larger backlogs are delivered over successive polls. Event history is durable and currently has no retention cleanup.
