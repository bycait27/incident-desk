# F11 — Live incident updates with Server-Sent Events

## Design and delivery guarantees

Server-Sent Events (SSE) are used because incident changes flow from the backend to read-only status-board clients; the browser does not need a persistent bidirectional channel. The browser's native `EventSource` automatically reconnects and sends the last received event ID.

Every successful incident submission, update, publish, or archive writes a full snapshot to the append-only `incident_events` table in the same database transaction as the incident and audit-log change. New submissions are private until an operator publishes them. Public/viewer snapshots and SSE streams never expose private report contents; operator streams receive all active reports. Archiving hides a report while preserving its incident, audit, and event history. Writers lock one database row before inserting an event, ensuring generated event IDs follow commit order even when writes overlap. The event table's generated ID is the SSE event ID. The stream queries rows with IDs greater than the subscriber's cursor, in ascending order, in batches of at most 100. Events are retained in PostgreSQL so reconnecting after a network interruption or backend restart can replay missed changes.

The initial `GET /api/incidents` response includes `X-Incident-Event-Cursor`. Its incident snapshot and cursor are read in one repeatable-read transaction, avoiding a gap between loading the current data and opening the stream. The frontend connects to `GET /api/incidents/events?after=<cursor>`; the server resumes from the higher of the initial cursor and `Last-Event-ID`. The frontend ignores repeated or older IDs and upserts each incident by ID, preventing duplicate cards. Heartbeat comments keep idle streams active.

## Automated evidence

**Hand-predicted expected results before running:** a viewer submission creates a private `CREATED` event; anonymous/viewer streams skip its content while advancing past its ID; an operator can see and publish it; publishing emits a public event; an archive emits a removal event without deleting history; a snapshot exposes the latest event cursor; reconnecting with a later `Last-Event-ID` resumes after that ID; repeated frontend event IDs do not duplicate incidents.

Run the backend and frontend checks from the repository root:

```powershell
mvn -f backend/pom.xml verify
cd frontend
npm run typecheck
npm run test
npm run lint
npm run build
```

The backend tests use synthetic incidents and mock repositories; frontend tests use a mocked `EventSource`. They do not require a live account or external service.

Observed: `mvn -f backend/pom.xml verify` passed all 38 backend tests. Frontend `npm run typecheck`, `npm run test` (16 tests), `npm run lint`, and `npm run build` all passed.

## Limits

SSE is one-way; browser-to-server actions use authenticated, CSRF-protected REST endpoints. The per-connection poll reads at most 100 rows each second, so larger backlogs are delivered over successive polls. Event history is durable and currently has no retention cleanup.
