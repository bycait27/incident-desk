# F7 — Google OIDC login

## Status

The application is wired for Google OpenID Connect Authorization Code login. A live Google sign-in completed, and the redacted browser trace is saved as `F7-login-redacted.har`.

## Implementation

Spring Security's OAuth2 Client handles the redirect, callback, session state, and OIDC nonce validation. The authorization request explicitly adds PKCE using S256. `GoogleOAuth2ClientConfigTest` checks that the generated request contains `response_type=code`, state, nonce, `code_challenge`, and `code_challenge_method=S256`.

The Google sign-in link is hidden unless the frontend has `VITE_GOOGLE_OAUTH_ENABLED=true`. Google client credentials stay on the backend; `GOOGLE_CLIENT_SECRET` must never be copied into a `VITE_` variable or committed. Anonymous incident reads remain public. F9 further restricts incident writes to operators.

## Configure a local Google OAuth client

1. In Google Cloud Console, configure the OAuth consent screen and add the account used for testing as a test user.
2. Create an OAuth client with application type **Web application**.
3. Add this authorized redirect URI: `http://localhost:8080/login/oauth2/code/google`.
4. Configure the backend environment in the shell that will run Spring Boot:

   ```powershell
   $env:GOOGLE_OAUTH_ENABLED = 'true'
   $env:GOOGLE_CLIENT_ID = '<client ID from Google Cloud Console>'
   $env:GOOGLE_CLIENT_SECRET = '<client secret from Google Cloud Console>'
   $env:FRONTEND_URL = 'http://localhost:5173'
   ```

   Do not paste the values into chat or source control. Keep the secret in a local environment or secret store.
5. Copy `frontend/.env.example` to the ignored `frontend/.env.local`, change `VITE_GOOGLE_OAUTH_ENABLED=false` to `true`, then start PostgreSQL, the Spring backend, and the Vite frontend.
6. Use **Sign in with Google**. Confirm that Google sends the browser to the configured callback and the app returns to `/?login=success`.
7. Capture the browser network flow as a HAR with Preserve log enabled. Redact authorization codes, cookies, ID/access tokens, and client-secret fields before retaining it. Keep the unredacted HAR private and delete it after producing the redacted evidence.

Local run commands, from the repository root:

```powershell
docker compose -f docker/docker-compose.yml up -d
Copy-Item frontend/.env.example frontend/.env.local
```

In the backend shell, set the four server variables above, then run:

```powershell
Set-Location backend
mvn spring-boot:run
```

In a second shell:

```powershell
Set-Location frontend
npm ci
npm run dev
```

The tests verify that enabling login without server-side credentials fails, and that the authorization request includes `response_type=code`, state, nonce, and an S256 PKCE challenge.

## Live-flow evidence

`F7-login-redacted.har` is a minimized, redacted derivative of the browser capture. It preserves 11 relevant requests from the successful flow: frontend load, backend authorization redirect, Google authorization/consent redirects, the backend callback, and the redirect back to the frontend with `login=success`. The trace confirms `response_type=code` and `code_challenge_method=S256`.

**Redaction attestation:** OAuth code, state, nonce, client ID, and other query values are redacted except non-sensitive protocol indicators. Request/response headers, cookies, and bodies were removed; no email-shaped values remain. The original unredacted HAR must not be committed or redistributed.

## Interpretation, AI use, and limits

Spring Security supplies OAuth/OIDC protocol handling; the app does not collect or store passwords. The request test was added because PKCE is not guaranteed merely by selecting the authorization-code grant; the resolver explicitly applies the PKCE customizer. The Google client ID and secret are not present in the repository. The test uses synthetic credentials; the live-flow artifact is redacted.

F7's live login and redacted HAR are demonstrated. F8's server-side validation is documented in `F8.md`; F9 must map validated identity claims to roles.
