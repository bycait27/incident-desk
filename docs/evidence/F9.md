# F9 — Viewer and operator roles

## Role source and enforcement

After Spring Security validates the Google OIDC ID token, `GoogleRoleAuthoritiesMapper` reads its `sub` claim. A subject exactly matching the backend-only `GOOGLE_OPERATOR_SUBJECT` setting receives `ROLE_OPERATOR`; every other subject, including when the setting is empty, receives `ROLE_VIEWER`. Existing `ROLE_*` authorities are discarded before the app role is assigned.

`GET /api/incidents/**` remains public. Every other method under `/api/incidents/**` requires `ROLE_OPERATOR`; other non-public endpoints require authentication. Anonymous writes receive 401, including requests rejected for missing CSRF tokens, and authenticated viewers receive 403. CSRF protection remains enabled. Write audit actors now come from the validated OIDC user's email claim, not the client-controlled `X-User-Email` header.

The authenticated `GET /api/auth/me` endpoint returns the current user's `sub` and assigned roles, allowing the app owner to configure the operator subject without logging or sharing tokens. To provision the operator locally, sign in, open `http://localhost:8080/api/auth/me`, and set the returned subject in the backend process environment:

```powershell
$env:GOOGLE_OPERATOR_SUBJECT = '<subject returned by /api/auth/me>'
```

Keep the subject value out of source control and chat. Restart the backend after setting it. An empty value safely leaves all users as viewers.

## Automated evidence

**Hand-predicted expected results before running:** the configured OIDC subject maps to operator; all other or missing subjects map to viewer; an anonymous write returns 401; a viewer write returns 403; an operator write succeeds; a spoofed `X-User-Email` value does not replace the validated user's email.

Reproduce from the repository root:

```powershell
mvn -f backend/pom.xml verify
```

Observed result:

```text
Tests run: 16, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

Role-mapper tests use synthetic OIDC subjects. MockMvc tests verify the actual 401 for an anonymous write, 403 for a viewer write with a valid CSRF token, and a successful operator write. The operator-write test verifies the controller passes the OIDC email claim to the service despite an attacker-supplied header.

## Interpretation, AI-use log, and limits

Google does not issue CampusPulse-specific roles by default. AI-assisted analysis considered the available OIDC claims; the user chose an allowlist keyed by the validated `sub` claim rather than granting operator to every authenticated Google account. This avoids trusting user-supplied identity headers and keeps role assignment server-side.

The tests are deterministic and do not use live Google tokens or a real user's subject. The environment value that grants operator access must be configured privately on the backend.

**Redaction attestation:** no live subject, email, client secret, token, or cookie is stored in this evidence. All test identities and credentials are synthetic.
