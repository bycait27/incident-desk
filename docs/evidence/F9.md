# F9 — Viewer and operator roles

## Role source and enforcement

After Spring Security validates the Google OIDC ID token, `GoogleRoleAuthoritiesMapper` reads its `sub` claim. A subject exactly matching the backend-only `GOOGLE_OPERATOR_SUBJECT` setting receives `ROLE_OPERATOR`; every other subject, including when the setting is empty, receives `ROLE_VIEWER`. Existing `ROLE_*` authorities are discarded before the app role is assigned.

`GET /api/incidents/**` is public but returns only published, non-archived incidents to anonymous users and viewers. An authenticated viewer may `POST /api/incidents` to submit a report; new reports are private until an operator publishes them. Only `ROLE_OPERATOR` may update, publish, or archive reports. Anonymous writes receive 401, while viewers receive 403 for operator-only writes. CSRF protection remains enabled, with a session-bound token fetched from `GET /api/auth/csrf`. Write audit actors come from the validated OIDC user's email claim, not a client-controlled header.

The authenticated `GET /api/auth/me` endpoint returns the current user's `sub`, email, and assigned roles, allowing the app owner to configure the operator subject without logging or sharing tokens. To provision the operator locally, sign in, open `http://localhost:8080/api/auth/me`, and set the returned subject in the backend process environment:

```powershell
$env:GOOGLE_OPERATOR_SUBJECT = '<subject returned by /api/auth/me>'
```

Keep the subject value out of source control and chat. Restart the backend after setting it. An empty value safely leaves all users as viewers.

## Automated evidence

**Hand-predicted expected results before running:** the configured OIDC subject maps to operator; other authenticated subjects map to viewer; an anonymous submission returns 401; a viewer submission creates a private incident with 201 and a `Location`; a viewer update returns 403; an operator update/publish/archive succeeds; a spoofed `X-User-Email` value does not replace the validated user's email.

Reproduce from the repository root:

```powershell
mvn -f backend/pom.xml verify
```

Observed result:

```text
Tests run: 13, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

The controller tests use synthetic OIDC identities and verify the 401, 403, 201 + `Location`, 200, 204, 400, and 409 cases; they also exercise the CSRF token round trip and the exact-origin CORS allowlist. Role-mapper tests verify the operator subject mapping. Actor-attribution tests confirm that the service receives the validated OIDC email rather than the spoofed header.

## Interpretation, AI-use log, and limits

Google does not issue Incident Desk-specific roles by default. AI-assisted analysis considered the available OIDC claims; the user chose an allowlist keyed by the validated `sub` claim rather than granting operator to every authenticated Google account. This avoids trusting user-supplied identity headers and keeps role assignment server-side.

The tests are deterministic and do not use live Google tokens or a real user's subject. The environment value that grants operator access must be configured privately on the backend. Viewers must sign in before submitting; anonymous write access remains blocked to preserve the validated-actor audit requirement.

**Redaction attestation:** no live subject, email, client secret, token, or cookie is stored in this evidence. All test identities and credentials are synthetic.
