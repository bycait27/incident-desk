# F8 — Server-side token validation

## Implementation

Spring Security's OIDC login validates the ID token on the server. The Google client registration pins the expected issuer and JWKS endpoint; Spring's `OidcIdTokenDecoderFactory` uses Nimbus to verify the JWT signature and the built-in OIDC validators check required claims, issuer, audience, and expiration.

The OIDC user service separately validates the scopes granted with the access token before loading user information. It requires `openid`, `email`, and `profile`, and normalizes Google's documented UserInfo scope URI aliases. Missing scopes fail authentication with `insufficient_scope`.

## Interpretation, AI-use log, and limits

Spring's OIDC defaults cover signature, issuer, audience, and expiry for ID tokens, but do not enforce which scopes the provider granted. The scope validator is explicit application logic rather than an assumption that requesting a scope means it was granted. Google scope URI aliases are normalized before checking the required set.

AI helped identify Spring Security's OIDC extension points. We checked the claim that requesting scopes guarantees they were granted against the token-response behavior; this implementation checks the access token's granted scopes explicitly.

The live Google login in F7 demonstrates the provider round trip. F8's negative cases are deterministic local tests; they do not call Google's JWKS service or use a real user's token. The live-flow HAR is redacted; the tests use synthetic token material.

**Redaction attestation:** all test keys, tokens, subjects, and client identifiers are synthetic; no credentials, personal data, or live tokens are included.
