# F10 — Better Stack monitoring integration

## Integration design

The backend reads a team-scoped Better Stack Incidents API token from `BETTERSTACK_API_TOKEN`; the token is never sent to or embedded in the frontend. The integration requests `GET https://incidents.betterstack.com/api/v2/monitors?per_page=250` with Bearer authentication. Better Stack's [official API documentation](https://betterstack.com/docs/uptime/api/list-all-existing-monitors/) documents the endpoint, authentication, JSON:API response, pagination, status values, and a maximum page size of 250.

Only monitor IDs explicitly listed in `BETTERSTACK_PUBLIC_MONITOR_IDS` are returned by the public endpoint. Create synthetic public monitors and use a team-scoped Incidents API token. This avoids exposing other monitors, including internal URLs and names, that may be present in the Better Stack team. The API reads at most the first 250 monitors per refresh, so configured public IDs must appear on that page.

The backend applies a 2-second connect timeout and a 3-second read timeout, retries a transient network or 5xx failure once, and does not retry 4xx responses. A successful response is runtime-validated before caching: the JSON:API data array, monitor type, ID, URL, supported status, and optional ISO timestamp must have the expected shapes. Invalid provider data is not exposed as valid monitor status.

The cache holds validated results for 60 seconds, limiting requests to at most one page per minute per backend instance. This is intentionally conservative because the provider documentation specifies paging but does not publish an API rate limit; monitoring checks themselves are configured on intervals such as 30 seconds. On provider failure, the last successful response may be served as stale for up to 15 minutes. Without usable cached data, the API returns a degraded response while the incidents service remains available.

## Secret configuration

Configure `BETTERSTACK_API_TOKEN` only in the backend process environment or the deployment platform's secret store. For local PowerShell testing:

```powershell
$env:BETTERSTACK_API_TOKEN = '<token configured privately in Better Stack>'
$env:BETTERSTACK_PUBLIC_MONITOR_IDS = '<comma-separated IDs of synthetic public monitors>'
```

Do not commit the value, place it in a `VITE_` variable, or paste it into chat. The application remains runnable without a token and displays an explicit not-configured state.

## Automated evidence

**Hand-predicted expected results before running:** a valid synthetic Better Stack response maps only the explicitly allowlisted monitor and sends the Bearer token; the unallowlisted synthetic internal monitor is omitted; repeated requests within 60 seconds use the cache; a persistent 503 or timeout causes exactly two provider attempts and returns a degraded response; a provider outage after a successful fetch returns stale cached status; malformed response data is rejected without retry. Frontend tests predict visible loading, empty, transport-error/retry, and provider-degraded states.

Run all backend and frontend tests from the repository root:

```powershell
mvn -f backend/pom.xml verify
cd frontend
npm run typecheck
npm run test
```

The backend tests use `MockRestServiceServer` and a synthetic token; they do not call Better Stack or use a live credential. Frontend tests mock the backend endpoint. A live provider smoke test requires the owner to configure a private Better Stack token and allowlist at least one synthetic monitor ID.

Observed: `mvn -f backend/pom.xml verify` passed all 23 backend tests. Frontend `npm run typecheck`, `npm run test` (5 tests), `npm run lint`, and `npm run build` all passed.

## Interpretation and limits

This integration is read-only. It requests one page of at most 250 monitors; additional pages are intentionally not fetched, keeping provider request volume bounded. Cache state is in-memory and per backend instance; a restart clears it. During a provider outage, data older than 15 minutes is not represented as current. A live provider smoke test still requires private token and monitor-ID configuration; the committed tests use only synthetic values.

**Redaction attestation:** no live token, account identifier, or provider response is stored in this evidence. Test credentials and monitor data are synthetic.
